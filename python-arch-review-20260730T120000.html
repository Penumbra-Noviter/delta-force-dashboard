Python Architecture Review

Profit Calculator · 2026-07-30

v2 (PySide6)

Desktop profit-tracking app, PySide6 UI + pyqtgraph charts. 16 Python modules, ~2.2k LOC, 103 pytest tests. Migrated from Tkinter; single-instance, atomic JSON persistence, dark/light theme.

1. Business logic returning presentation colors

Strong

Files

  • calculator.py — ProfitCalculatorLogic.format_rate(), get_pnl_label()
  • config.py — get_color(), THEMES dict (called by calculator)
  • app/table_widget.py — consumer that re-derives color from rate

Problem

ProfitCalculatorLogic.format_rate() and get_pnl_label() return color hex strings ("#16a34a") alongside formatted text — business logic leaking presentation concerns. calculator.py imports get_color from config to compute display values.

Solution

Return structured data (rate value, PnL enum) from business methods; remove all color-aware logic from ProfitCalculatorLogic. The UI layer maps semantic values to theme colors.

Benefits

  • Protocol shrinks — cleaner return types
  • Locality restored — color logic lives in UI
  • Dependency direction fixed — calculator stops importing config.get_color
  • Seam appears — calculator testable without color module
  • Enables Candidate 2 (theme consolidation)

Python Analysis

  • Friction signals: Boundary leak — business layer calls get_color(…) for display purposes
  • Import graph: calculator → config::get_color (UI dependency in domain logic)
  • Method signatures: format_rate(rate: float | None) → tuple[str, str] — second str is a hex color
  • Test impact: test_calculator.py imports get_color to assert color values
  • Call sites: table_widget.py calls both format_rate() and get_pnl_label(), uses colors inline

2. Fragmented theme surface

Strong

Files

  • config.py — THEMES, get_color(), get_theme(), set_theme()
  • app/theme.py — re-exports from config + generate_qss()
  • app/__init__.py — re-exports 3 functions from app.theme

Problem

The theme system is fractured across config.py, app/theme.py, and app/__init__.py with a re-export chain. Consumers import get_color from three different paths (config, app.theme, app) depending on which layer they live in.

Solution

Move all theme data (THEMES, get_color, set_theme, get_theme) out of root config.py into app/theme.py. Root config keeps only path/font/date constants. The re-export in app/__init__.py is removed — consumers import directly from app.theme.

Benefits

  • Protocol shrinks — three export paths collapse to one
  • Locality restored — theme owns theme data
  • Dependency direction clarified — UI depends on app.theme, not root config

Python Analysis

  • Friction signals: Pass-through (app/__init__.py re-exports without abstraction), Undefined surface (intent unclear)
  • Import graph — current:
  • calculator → config.get_color
    data_store → config.DATA_FILE
    table_widget → app.theme.get_color
    input_panel → app.theme.get_color
    chart_widget → app.theme.get_color
    main_window → config.DATE_FORMAT + app.theme.get_color
    app → app.theme.get_color (re-export)
  • Dependency: Candidate 1 must be resolved first — calculator.py must stop importing get_color before theme data can move

3. MainWindow lacks dependency injection seam

Worth exploring

Files

  • app/main_window.py — MainWindow.__init__
  • data_store.py — DataStore (hard-created)
  • calculator.py — ProfitCalculatorLogic (hard-created)

Problem

MainWindow.__init__() creates DataStore() and ProfitCalculatorLogic(self.data) inline with no injection point. Testing the window with controlled data requires mocking or knowledge of internal attributes.

Solution

Accept store and logic as optional __init__ parameters (defaulting to fresh instances). Verify_All tests can inject mock stores without replacing SETTINGS_FILE or relying on side effects.

Benefits

  • Seam appears — injection point for alternate implementations
  • Testability improved — verify_all.py avoids file I/O
  • Fat delegator sign reduced — constructor clarifies dependencies

Python Analysis

  • Friction signals: Fat Delegator (partial — 2 data deps, but UI deps are widgets, not delegations)
  • Current: self.store = DataStore(); self.data = self.store.load(); self.logic = ProfitCalculatorLogic(self.data)
  • ACID: DataStore handles file I/O and ProfitCalculatorLogic handles queries — separation is already clean, only the wiring is tight
  • Complexity: Low risk, high impact — constructor signature change only, no existing tests break

4. Undefined surface in UI modules

Worth exploring

Files

  • app/main_window.py
  • app/input_panel.py
  • app/table_widget.py
  • app/chart_widget.py

Problem

4 of 5 modules in app/ lack __all__. Internal helpers (_create_action_buttons, _set_validity_state, _update_theme_colors) are technically importable by convention only.

Solution

Add __all__ to each module, listing only the public class/function that constitutes its protocol surface.

Benefits

  • Protocol shrinks — explicit contract per module
  • Self-documenting — IDE shows __all__ as module API
  • Low effort — mechanical change, no behavioral effect

Python Analysis

  • Friction signals: Undefined Surface
  • Current exports (inferred by non-_ convention):
  • main_window.py → MainWindow (real) + 15 non-private helpers
    input_panel.py → MoneyLineEdit, InputPanel (real) + 10 helpers
    table_widget.py → PnLBadge, _DaySubTable, TableWidget (real) + 12 helpers
    chart_widget.py → KMBAxisItem, ChartWidget (real) + 20 helpers
  • Contrast: modules outside app/ all define __all__

5. ChartWidget internal state sprawl

Speculative

Files

  • app/chart_widget.py (~500 lines)

Problem

ChartWidget manages 20+ instance variables tracking chart sub-elements (_plot_widget_top, _curve_top, _fill_warehouse, _vline_top, _hover_label_top, _proxy_top, …). Theme update requires manually updating each sub-element in sync.

Solution

Extract sub-element management into a _ChartPanel helper class that owns one plot (top or bottom) and its sub-elements. ChartWidget delegates to two _ChartPanel instances, halving its variable surface.

Benefits

  • Locality — per-panel concerns isolated
  • Deletion test — _ChartPanel earns its keep by halving repetitions
  • Verification surface reduced — each panel is independently testable

Python Analysis

  • Friction signals: Fat Delegator (toward pyqtgraph); Wrapper Cascade (no — methods are distinct)
  • Top/bottom panel code is ~80% identical — curve creation, fill, endpoint label, hover line, proxy, legend
  • _update_theme_colors(): 80 lines, must mirror _create_chart() structure exactly — invariant to maintain
  • Risk: medium churn for a file that works correctly; speculative until adjacent refactors land

Top Recommendation

Candidate #1: Extract presentation from ProfitCalculatorLogic — this is the keystone. Once format_rate() and get_pnl_label() return structured data instead of color strings, calculator.py no longer imports get_color(), which unblocks moving theme data from config.py to app/theme.py (Candidate #2). Without this fix, any theme refactoring must account for a business-logic import that shouldn't exist.

Effort: ~1 hour · Protocol surface reduction: 2 fewer imports · Cascade unlocks: 1 other Strong candidate + 1 Worth exploring
